# Data model

Only two data sets:
1. **The catalogue** (owned by the tool, versioned, generated by extraction + validation).
2. **The level** (read from the .esp, never duplicated; the tool derives a "grid" view from it).

EditorIDs in the examples are illustrative; the real ones will come from extraction.

## 1. Catalogue

### 1.1 Kit
```json
{
  "kit": "Imperial",
  "module": { "xy": 128, "z": 128 },
  "note": "measured (R5, smallhall): base tile 256 x 256, stairs +256; 128 and 64 variants. Module 128 proposed (D51). The vanilla free wall has a 384 core."
}
```
Measured example (`imphall1way01`, module 128): `pivot: [128, 128, -8]`, `cells` = 2 × 2 × 1
(`[0,0,0] [1,0,0] [0,1,0] [1,1,0]`), openings at -Y and +Y on both cells of each side.
`imphall1way128l01`: `pivot: [256, 128, -8]`, 3 × 2 cells, +Y exit shifted by -128.

### 1.2 Piece
```json
{
  "editorId": "ImpHallExemple01",
  "formKey": "0xxxxxx:Skyrim.esm",
  "model": "dungeons\\imperial\\...\\exemple.nif",
  "kit": "Imperial",
  "class": "tile",
  "category": "hall",
  "pivot": [0, 0, 0],
  "cells": [[0, 0, 0]],
  "faces": [
    { "cell": [0, 0, 0], "dir": "+X", "conn": "ImpHallSm" },
    { "cell": [0, 0, 0], "dir": "-X", "conn": "ImpHallSm" }
  ],
  "walkable": null,
  "obstacle": null,
  "review": { "auto": true, "validated": false }
}
```

| Field | Role | Required |
|---|---|---|
| `editorId`, `formKey`, `model` | identity; `formKey` is used to recognize the base of a ref read back | V1 |
| `class` | `tile` or `prop` | V1 (tile only) |
| `category` | hall / room / door (UI filtering) | V1 |
| `pivot` | position of the NIF origin relative to the min corner of the piece's cell (0,0,0), rotation 0 | V1 |
| `cells` | occupied grid cells, 3D indices, rotation 0. In V1 all z = 0 | V1 |
| `faces` | **open** faces only; a missing face is closed. `dir` ∈ ±X, ±Y, ±Z. `conn`: a type, or a list for composite profiles (D56, `implhalldoor*`) | V1 (±X, ±Y) |
| `walkable` | walkable polygon(s), vertices with Z, in local coordinates | NavMesh |
| `obstacle` | floor footprint(s) to cut holes in the NavMesh (props, then furniture) | Obstacles |
| `review` | proposed by analysis vs validated by hand | V1 |

Why 3D indices from V1 on: a staircase or a sloped hallway is simply a tile whose `cells` span two Z slices, with open faces at different z. Floor "quantization" falls out of the model; no format migration when Z arrives.

### 1.3 Connection type
```json
{
  "id": "ImpHallSm",
  "kit": "Imperial",
  "signature": "identifier of the group of equivalent profiles (open edges on the junction plane, normalized polylines)",
  "mate": "ImpHallSm",
  "navEdge": null
}
```
- Two faces fit together if they face each other and the `conn` of one = the `mate` of the other. `mate` = itself for a symmetric profile; otherwise it points to the mirror profile (left/right).
- `signature` is not a raw hash: profiles are compared with tolerance and grouped (exact → automatic, close → human validation); see R3.
- The profile includes its **z** (floor of the opening relative to the cell floor): R5 showed that this z varies by piece family (D55).
- Profile format (R3): polylines `[u1, v1, u2, v2]` in units, u to the right as seen from outside the piece, origin at the center of the cells covered by the opening, v = z minus level × Z module. Two faces looking at each other see the same geometry mirrored: `mate` = group of the mirror profile, itself if symmetric. Comparison tolerance: 8 units.
- `navEdge` (later): canonical endpoints of the walkable edge on this face. This is what guarantees that two separately baked NavMesh batches coincide.
- A piece-to-piece table is **not** stored: it grows as n² and breaks with every piece added. It is derived from the types.

### 1.4 Prop (later)
Same record as the piece with `class: "prop"`, without `cells` or `faces`, with `obstacle` and possibly:
```json
"snapHints": [ { "kind": "cellCorner" }, { "kind": "step", "axis": "X", "size": 128 } ]
```
(e.g. pillars at cell corners; L/M/R free walls at a 128 step.)

## 2. Level (view derived from the .esp)

What the tool reads for each ref of the cell:
```json
{ "refFormKey": "...", "base": "...", "pos": [x, y, z], "rot": [rx, ry, rz], "scale": 1.0 }
```

Deriving a tile placement:
- the base is in the catalogue with `class: tile`;
- `rx = ry = 0`, `rz` a multiple of 90° (tolerance), `scale = 1`;
- `pos` minus the rotated pivot falls on the grid (tolerance).

→ `{ "cell": [i, j, k], "rotation": 0..3 }`. Otherwise the ref is **opaque**: displayed, never modified.

On write: the inverse (cell + rotation + pivot → world pos/rot). Existing refs keep their FormID; only new tiles create refs.

Occupancy: the set of occupied cells (all tiles) is used to detect overlaps and to find free open faces.

## 3. Baked outputs (later)
- NavMesh: NAVM records in the cell. "Covered tile" = a geometric test on the existing triangles, so no data to store.
- Tool-specific state, if any is needed (lock, list of created NAVMs): minimal side file next to the plugin. Open question.

## 4. Minimum for V1
Catalogue: `editorId`, `formKey`, `category`, `pivot`, `cells` (z = 0), `faces` (±X/±Y) + connection types (`id`, `mate`). Everything else can stay `null`.
